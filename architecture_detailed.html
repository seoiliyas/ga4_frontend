1
Static Asset Delivery: The user's browser loads the React SPA from Cloudflare Pages — either brighthorizon-gtm.pages.dev (GTM mode, port 5173 in dev) or brighthorizon-ga4.pages.dev (GA4 mode, port 5174). No server-side rendering; the app boots entirely client-side.
2
Edge Routing via Worker: All API traffic (REST + SSE) is directed to the single Cloudflare Worker (worker/index.ts). It handles Auth, Sessions, Chat, and GA4 OAuth routes. In local dev, Vite proxies these requests to Wrangler Dev on port 8787.
3
Storage Layer: The Worker reads and writes to two Cloudflare storage primitives — D1 (gtm_chat_history) for relational data (users, sessions, messages) and KV (GTM_CONTAINER) for fast cache reads of large GTM container JSON blobs.
4
AI Interaction via Gemini: The Worker forwards the user prompt + chat history to Google Gemini using context caching for large GTM payloads (cache stored in KV with 30-minute TTL), then streams the response back via SSE (GTM mode) or returns JSON (GA4 mode).
5
GA4 Function Calling: In GA4 mode, Gemini issues up to 20 function-call turns. The Worker intercepts each call, executes it against the GA4 Data API or GA4 Admin API, and optionally renders charts via QuickChart.io before returning results to Gemini for synthesis.

1
App Bootstrap: main.tsx is the Vite entry point. It mounts the root React tree and sets environment-specific flags (API base URL, app mode identifier) that flow down through the component tree.
2
Context Wrapping: App.tsx wraps the entire subtree in AuthProvider (from the shared package), which exposes the useAuth hook. It also wraps in ToastProvider for global notifications. Both apps (GTM and GA4) do this identically.

6
Utility Helpers: clean-json.ts sanitizes AI responses before rendering, and gtm-minifier.ts compresses large GTM container JSON before uploading to the Worker, keeping payloads within limits.

1
Unified Entry + CORS: Every request enters through the Worker's fetch handler in index.ts. CORS preflight (OPTIONS) is handled globally first, ensuring cross-origin requests from Cloudflare Pages succeed.
2
Open Auth Routes: /api/auth/bootstrap, /api/auth/signup, and /api/auth/login require no Bearer token — they are public. However, /api/auth/me, /api/auth/invite, and /api/auth/invite-keys are internally guarded by the auth middleware.
3
Protected Route Guard: All session and chat routes require a valid Bearer token. The authenticate() middleware JOINs auth_tokens and users in D1, rejects expired tokens, and attaches the user object to the request context before routing continues.
4
Chat Mode Dispatch: POST /api/chat reads chatMode from the body ('gtm' or 'ga4') and delegates to either gtm-chat.ts (SSE streaming) or ga4/chat.ts (function-calling JSON). Both share the same route but diverge completely in implementation.
5
GA4 OAuth Redirect Flow: /api/ga4/oauth/authorize redirects users to Google's consent screen. Google sends them back to /api/ga4/oauth/callback, where the Worker exchanges the authorization code for tokens and stores them in ga4_oauth_tokens in D1.
6
App Context Inference: When OAuth callbacks arrive (no app header), the Worker infers the intended app from the request URL or state parameter, ensuring tokens are associated with the correct user and app mode.

1
User Identity (users): Stores the canonical user record with a TEXT id (PK), unique username and email, PBKDF2-hashed password, and an app field to scope the user to GTM or GA4 mode.
2
Session Tokens (auth_tokens): Each login generates a new row with a random token (PK), user_id FK, and an expires_at Unix timestamp 30 days in the future. Multiple tokens per user are supported (multi-device).
3
Invite System (invite_keys): One-time-use keys are created by an admin via POST /api/auth/invite. The used_by and used_at columns are populated atomically during signup, preventing replay. Each key is also scoped to an app.
4
Audit Sessions (sessions): Represents a conversation thread. Stores a title (auto-generated after the first AI reply), mode ('gtm' or 'ga4'), and optionally a ga4_property_id for GA4 sessions.
5
Message History (messages): Each row stores role ('user' or 'model'), full text, and a charts JSON field for any QuickChart URLs embedded in GA4 responses. Cascade-deleted when the parent session is deleted.
6
GA4 OAuth Tokens (ga4_oauth_tokens): Keyed by user_id (one row per user), stores the Google access_token, refresh_token, token_expiry, granted scope, and connected_email. The Worker refreshes the access token automatically when it expires.

Logic Flows & Interactions

Step-by-step sequences of the most complex system operations.

GTM Chat Streaming (SSE)

sequenceDiagram
    participant U as User (Browser)
    participant D as Dashboard.tsx
    participant C as chatApi.ts
    participant W as Worker (CF)
    participant DB as D1 Database
    participant KV as KV Store
    participant G as Gemini API

    U->>D: Types question + clicks Send
    D->>D: Append user msg to state
    D->>D: Append empty model msg placeholder
    D->>C: sendMessageStream(sessionId, question)
    C->>W: POST /api/chat {sessionId, question, mode: "gtm"}

    W->>DB: Verify session ownership
    W->>DB: Load message history (SELECT)
    W->>KV: Check cached Gemini context

    alt Cache exists
        KV-->>W: Return cache name
    else Cache expired
        W->>G: Create new context cache (container JSON)
        G-->>W: Return cache name
        W->>KV: Store cache name (TTL 30m)
    end

    W->>G: generateContentStream(history + question)

    loop SSE chunks
        G-->>W: text chunk
        W-->>C: data: {"text":"..."}
        C-->>D: onChunk(text)
        D->>D: Append chunk to model msg
    end

    W-->>C: data: [DONE]
    W->>DB: INSERT user + model messages
    W->>DB: UPDATE session.updated_at

    D->>D: Auto-title if first reply
    D->>C: renameSession(title)
    C->>W: PATCH /api/sessions/:id
1
Optimistic UI Update: Before the network request fires, Dashboard.tsx appends the user's message to local state and immediately inserts an empty model message placeholder. This gives the user instant visual feedback.
2
POST to Chat Route: chatApi.sendMessageStream() sends POST /api/chat with body {sessionId, question, mode: "gtm"}. The Worker first verifies session ownership (D1 JOIN on sessions and users), then loads full message history via SELECT.
3
KV Cache Check: The Worker checks KV for a cached Gemini context name keyed to the GTM container ID. If the cache exists and is within its 30-minute TTL, the cache name is reused, avoiding re-uploading the entire container JSON to Gemini.
4
Cache Miss — Context Creation: If KV returns nothing (or the cache expired), the Worker calls Gemini to create a new context cache from the container JSON, receives the cache name back, then writes it to KV with a 30-minute TTL for future requests.
5
SSE Stream: generateContentStream(history + question) is called against Gemini. As each text chunk arrives, the Worker immediately flushes it to the client as data: {"text":"..."}\n\n. chatApi.ts reads the ReadableStream and calls onChunk(text) to append each token to the placeholder message in the Dashboard.
6
Stream Termination: After the last chunk, the Worker sends data: [DONE] to signal completion. It then writes both the user message and the full assembled model message into D1 (INSERT into messages) and updates sessions.updated_at.
7
Auto-Title: If this was the first AI reply in the session, Dashboard.tsx extracts a title from the response and calls chatApi.renameSession() → PATCH /api/sessions/:id, updating the sidebar entry automatically.

GA4 Function Calling Flow

sequenceDiagram
    participant U as User (Browser)
    participant D as Dashboard.tsx
    participant C as chatApi.ts
    participant W as Worker (CF)
    participant DB as D1 Database
    participant G as Gemini API
    participant GA4 as GA4 APIs
    participant QC as QuickChart.io

    U->>D: Types question + clicks Send
    D->>C: sendMessage(sessionId, question, mode: "ga4")
    C->>W: POST /api/chat {sessionId, question, mode: "ga4"}

    W->>DB: Verify session ownership
    W->>DB: Load message history

    Note over W: Auth validates: Bearer token + X-BrightHorizon-App header

    loop Up to 20 tool turns
        W->>G: generateContent() with 9 function declarations
        G-->>W: function_call (e.g., runReport or create_chart)
        alt GA4 API call
            W->>GA4: Execute GA4 API call
            GA4-->>W: Return data
        else Chart rendering
            W->>QC: QuickChart.io API
            QC-->>W: Return chart image URL
        end
        W->>G: Return function result
    end

    G-->>W: Final text response
    W-->>C: JSON response
    C-->>D: onMessage(text)
    D->>DB: INSERT user + model messages
1
JSON Response Mode: Unlike GTM's SSE stream, the GA4 chat route returns a single JSON response after all function-calling turns complete. chatApi.sendMessageStream() handles both modes — it detects the content type and invokes onMessage(text) for GA4 instead of onChunk().
2
Session & Auth Validation: The Worker verifies session ownership in D1, loads full message history, and validates the Bearer token + X-BrightHorizon-App header (or infers the app from the URL for OAuth callback paths) before proceeding.
3
Gemini Function Declaration: The Worker calls generateContent() with 9 pre-declared function schemas (e.g., runReport, listDimensions, create_chart). Gemini reads the user's question and selects the most appropriate tool to call.
4
Function Execution Loop (up to 20 turns): Gemini returns a function_call block. The Worker's executeGA4Function() in services/ga4/api.ts dispatches to either the GA4 Data API or GA4 Admin API using the user's OAuth access token (refreshing it if expired).
5
Chart Rendering Branch: If Gemini calls create_chart, the Worker delegates to services/ga4/tools/charts.ts, which builds a QuickChart.io API request, retrieves a chart image URL, and packages it as a function_result back to Gemini.
6
Iterative Grounding: Each function_result is fed back into Gemini as part of the conversation. Gemini may issue another function_call (e.g., first fetching data then charting it). This loop continues until Gemini produces a final text response.
7
Response Persistence: Once the final text response is assembled (with any embedded chart URLs in the charts field), the Worker returns the JSON to the client. Dashboard.tsx then INSERTs both the user and model messages into D1.

Authentication Flow

sequenceDiagram
    participant U as User
    participant AP as AuthPage
    participant AC as AuthContext
    participant AA as authApi.ts
    participant W as Worker
    participant DB as D1

    Note over U,DB: --- Sign Up (First User — Bootstrap) ---

    U->>AP: Fill username, email, password
    AP->>AC: bootstrap(username, email, password)
    AC->>AA: authApi.bootstrap(...)
    AA->>W: POST /api/auth/bootstrap
    W->>DB: COUNT users
    DB-->>W: 0 users
    W->>W: hashPassword (PBKDF2)
    W->>DB: INSERT user
    W->>W: generateToken()
    W->>DB: INSERT auth_token (30-day expiry)
    W-->>AA: {token, user}
    AA-->>AC: setToken + setUser
    AC-->>AP: isAuthenticated = true
    AP-->>U: Redirect to Dashboard

    Note over U,DB: --- Subsequent Login ---

    U->>AP: Fill email, password
    AP->>AC: login(email, password)
    AC->>AA: authApi.login(...)
    AA->>W: POST /api/auth/login
    W->>DB: SELECT user by email
    W->>W: verifyPassword (PBKDF2)
    W->>DB: INSERT new auth_token
    W-->>AA: {token, user}

    Note over U,DB: --- Token Validation on Reload ---

    U->>AP: Page refresh
    AC->>AC: getToken() from localStorage
    AC->>AA: authApi.getMe()
    AA->>W: GET /api/auth/me (Bearer token + X-BrightHorizon-App header)
    W->>DB: JOIN auth_tokens + users
    W-->>AA: {user}
    AA-->>AC: setUser (session restored)
    AC-->>AP: isAuthenticated = true
    AP-->>U: Resume Dashboard (no re-login needed)
1
Bootstrap (First User): If no users exist in D1, the first registration bypasses invite keys. The Worker COUNTs rows in users and proceeds only when the count is 0.
2
Invite-Key Signup: Subsequent users must supply a valid one-time invite key. The Worker validates the key, marks it as used (used_by, used_at), then creates the account.
3
Password Hashing: On both signup and login, passwords are processed with PBKDF2 + a random salt. Plain-text passwords are never written to D1.
4
Token Issuance: After a successful credential check, generateToken() produces a random Bearer token inserted into auth_tokens with a 30-day expires_at timestamp.
5
Client Persistence: The token is returned to authApi.ts, which stores it in localStorage. AuthContext sets isAuthenticated = true and redirects to the Dashboard.
6
Token Validation on Reload: On every page refresh, AuthContext reads the token from localStorage and calls GET /api/auth/me with a Bearer header and X-BrightHorizon-App. The Worker JOINs auth_tokens + users to verify expiry and return the user object — no re-login required.
7
Logout: Calling POST /api/auth/logout deletes the token row from D1 and clears localStorage, invalidating the session immediately on the server side.

1
Monorepo Root: package.json + pnpm-workspace.yaml declare the workspace, linking frontend/apps/gtm, frontend/apps/ga4, frontend/packages/shared, and the worker directory. All pnpm scripts (dev, build, deploy) run from the root.
2
App → Shared Dependency: gtm/src/App.tsx and ga4/src/App.tsx both import AuthContext, Dashboard, and Sidebar from @brighthorizon/shared. The shared package is referenced as a workspace package (no publishing required) and resolved via pnpm's symlink mechanism.
3
Worker Entry Point: worker/index.ts imports and registers all four route handlers — routes/auth.ts, routes/sessions.ts, routes/chat.ts, and routes/ga4-oauth.ts. It is the single file that Wrangler bundles and deploys.
4
Service Separation: Chat routes delegate to dedicated service files — services/gtm-chat.ts for SSE streaming and services/ga4/chat.ts for function calling. GA4 chat further depends on services/ga4/api.ts (API execution) and services/ga4/tools/charts.ts (QuickChart integration).
5
Cross-Cutting Utilities: middleware/auth.ts is shared by both routes/auth.ts and routes/ga4-oauth.ts for token validation. utils/crypto.ts provides PBKDF2 hashing used by routes/auth.ts. utils/http.ts supplies response helpers used across all routes.
6
Infrastructure as Code: wrangler.toml defines D1 and KV bindings, Worker name, and compatibility flags. schema.sql is the single source of truth for all 6 database tables and is applied via wrangler d1 execute on first setup or migration.
