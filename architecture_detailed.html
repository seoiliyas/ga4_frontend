1
Dual-App Client Delivery: Two Vite React 19 SPAs — @brighthorizon/gtm (:5173) and @brighthorizon/ga4 (:5174) — deploy to Cloudflare Pages and share UI, auth, and API clients from @brighthorizon/shared.
2
Portable API Runtime: All Web-standard route handlers live in worker/ and run identically on either Cloudflare Workers (worker/index.ts + daily Cron) or GCP Cloud Run via Node 22 + Hono (server/src/index.ts).
3
Abstracted Storage Primitives: Workers use native D1, KV, and R2 bindings, while Cloud Run shims (db.ts, kv.ts, r2.ts) adapt Cloud SQL Postgres and Google Cloud Storage buckets behind the exact same D1/KV/R2 interfaces.
4
Vertex AI Gemini & Context Caching: Powered by @google/genai (default gemini-2.5-flash, plus dynamic model discovery via GET /api/models). GTM mode caches the minified container in KV/GCS keyed by model + sha256(container) (1-hour TTL) and streams over SSE.
5
Parallel GA4 Tool Loop & Private Charting: In GA4 mode, Gemini issues up to 20 tool turns with parallel execution across 8 declarations (7 GA4 APIs + create_chart). Chart.js v4 PNGs are saved privately to R2/GCS at /api/files/:id and persisted in messages.charts.
6
Multimodal Files & Hardened Security: Supports image, PDF, text/CSV, and zero-dependency OOXML (.docx/.xlsx) attachments viewed via authenticated Blob URLs, protected by Bearer-only auth, PBKDF2, AES-GCM, HMAC OAuth state, rate limiting, and origin-allowlisted CORS.

1
User Identity (users): Composite unique constraints on (username, app) and (email, app) let the same person maintain separate accounts across GTM and GA4 apps, with salted PBKDF2-SHA256 passwords.
2
Session Tokens (auth_tokens): 30-day random Bearer tokens indexed on user_id and expires_at for fast auth and scheduled cleanup.
3
Invite System (invite_keys): Single-use INV-... keys with optional app scoping, ON DELETE CASCADE on creator, and ON DELETE SET NULL on redeemer.
4
Audit Sessions (sessions): Tracks mode ('gtm' | 'ga4'), title, optional numeric ga4_property_id, and BIGINT/INTEGER millisecond timestamps.
5
Message History (messages): Stores ordered conversation turns along with charts JSON (persisted GA4 chart URLs) and attachments JSON (linked file IDs).
6
GA4 OAuth Tokens (ga4_oauth_tokens): Stores AES-GCM encrypted Google access_token and refresh_token, expiry, scopes, and connected_email.
7
Attachments & Private Charts (attachments): Indexes every uploaded user file and privately stored GA4 chart PNG with its R2/GCS r2_key, owner, session, and optional message link.

Logic Flows & Interactions

End-to-end execution sequences for GTM SSE streaming, GA4 parallel tool calling, and auth/OAuth.

GTM Chat Streaming (SSE)

sequenceDiagram
    participant U as User (Browser)
    participant D as Dashboard.tsx
    participant C as chatApi.ts
    participant R as routes/chat.ts
    participant S as gemini-chat.ts
    participant DB as D1 / Postgres
    participant KV as KV / GCS
    participant G as Vertex AI Gemini

    U->>D: Types question / attaches files + clicks Send
    D->>D: Append user msg + empty model placeholder
    D->>C: sendMessageStream(sessionId, question, signal)
    C->>R: POST /api/chat {sessionId, question, chatMode: "gtm", model, attachmentIds}

    R->>DB: Verify session ownership + load history + loadAttachments()
    R->>KV: get("container", cacheTtl: 3600)
    R->>S: streamGtmChat(...)
    S->>KV: Check cache key (model + sha256(container))

    alt Cache exists & valid
        KV-->>S: Return cache name
    else Cache miss / expired
        S->>G: caches.create(model, containerJson, ttl: 3600s)
        G-->>S: Return cache name
        S->>KV: put(cacheKey, cacheName, expirationTtl: 3600)
    end

    S->>G: generateContentStream(history + question + fileParts)

    loop SSE chunks
        G-->>S: text chunk
        S-->>C: data: {"text":"..."}
        C-->>D: onChunk(text)
        D->>D: Append chunk to model msg
    end

    S-->>C: data: [DONE]
    S->>DB: INSERT user + model messages + link attachments
    S->>DB: UPDATE session.updated_at

    D->>C: renameSession(title) on first reply
    C->>R: PATCH /api/sessions/:id
1
Optimistic UI & Abort Support: Dashboard.tsx inserts the user turn and empty model placeholder immediately, passing an AbortController signal so users can cancel mid-stream via the Stop button.
2
Session, History & Attachment Validation: routes/chat.ts enforces rate limits, verifies session ownership, validates attachments belong to both user and session, and builds multimodal parts (including extracted .docx/.xlsx text).
3
Model + Hash Context Cache Check: getOrCreateCache() keys KV/GCS by gemini_gtm_context_cache:<model>:<hash>, ensuring switching between Flash and Pro never hits a cross-model cache mismatch.
4
Cache Miss / Inline Fallback: Creates a 1-hour (3600s) Vertex AI context cache if missing; if cache creation is unsupported or fails, falls back gracefully to inline system instruction injection.
5
Disconnect-Safe SSE Stream: Chunks stream as data: {"text":"..."} via TransformStream; write errors on client abort are caught cleanly without crashing the isolate.
6
Persistence & Auto-Title: Once streaming completes, streamGtmChat() writes both turns and attachment links to D1/Postgres, and the frontend auto-titles the session on its first reply.

GA4 Parallel Function Calling & Private Charting Flow

sequenceDiagram
    participant U as User (Browser)
    participant D as Dashboard.tsx
    participant C as chatApi.ts
    participant R as routes/chat.ts
    participant S as gemini-chat.ts
    participant G as Vertex AI Gemini
    participant GA4 as GA4 Data/Admin APIs
    participant QC as QuickChart v4
    participant Store as R2 / GCS + DB

    U->>D: Types GA4 question + clicks Send
    D->>C: sendMessageStream(sessionId, question, "ga4")
    C->>R: POST /api/chat {sessionId, question, chatMode: "ga4"}

    R->>Store: Verify session + ga4_property_id + load history
    R->>S: runGA4Chat(...)
    S->>Store: Decrypt + refresh GA4 OAuth access token

    loop Up to 20 tool turns (parallel Promise.all per turn)
        S->>G: generateContent() with 8 function declarations
        G-->>S: functionCalls[]
        par GA4 API tool calls
            S->>GA4: Execute GA4 Data / Admin REST call
            GA4-->>S: JSON metrics / dimensions
        and Chart tool calls
            S->>QC: POST /chart (version 4, PNG)
            QC-->>S: PNG binary bytes
            S->>Store: Save PNG to CHAT_FILES + attachments -> /api/files/:id
        end
        S->>G: Return functionResponses[]
    end

    G-->>S: Final candidate (thought parts filtered out)
    S-->>R: {answer, charts}
    R->>Store: INSERT user + model messages (with charts JSON)
    R-->>C: JSON {answer, charts}
    C-->>D: Render Markdown + fetch charts via AuthImage
1
JSON Tool-Loop Mode: POST /api/chat with chatMode: "ga4" invokes runGA4Chat(), passing the session's bound ga4_property_id and the user's decrypted (and auto-refreshed) Google OAuth access token.
2
8 Function Declarations: Exposes 7 GA4 Data/Admin API tools (with strict numeric property ID validation and optional dimensions) plus create_chart (without exposing any third-party API keys to the LLM).
3
Parallel Tool Execution: Multiple function calls issued in a single Gemini turn execute concurrently via Promise.all() across up to 20 sequential turns.
4
Chart.js v4 Private Storage: createChart() posts Chart.js v4 configs to QuickChart, saves PNGs directly into R2/GCS + attachments, and returns authenticated /api/files/:id URLs (falling back to ImgBB/shortUrl only when private storage is unavailable).
5
Thought Filtering & Persistence: Internal Gemini thought parts are stripped from textParts; routes/chat.ts persists both messages including the charts JSON column so charts survive reload, and AuthImage fetches them securely with Bearer auth.

Authentication & Signed GA4 OAuth Flow

sequenceDiagram
    participant U as User
    participant AP as AuthPage / Dashboard
    participant AC as AuthContext / chatApi
    participant W as API (Worker / Cloud Run)
    participant DB as D1 / Postgres
    participant G as Google OAuth 2.0

    Note over U,DB: --- Bootstrap / Atomic Invite Signup / Login ---
    U->>AP: Submits credentials (+ INV-key for signup)
    AP->>AC: bootstrap / signup / login
    AC->>W: POST /api/auth/... (rate limited)
    W->>DB: PBKDF2 hash/verify + atomic invite claim
    W-->>AC: {token, user} (30-day Bearer token)

    Note over U,G: --- HMAC-Signed GA4 OAuth Popup ---
    U->>AP: Clicks Connect GA4 Account
    AP->>AC: getGa4OAuthUrl() (Bearer Header)
    AC->>W: GET /api/ga4/oauth/authorize?format=json
    W->>W: signState({userId, ts, nonce, origin}, TOKEN_ENCRYPTION_KEY)
    W-->>AC: {url: accounts.google.com/...}
    AP->>G: Open popup to Google consent (analytics.readonly + userinfo.email)
    G-->>W: GET /api/ga4/oauth/callback?code=...&state=...
    W->>W: verifyState() + 10m TTL check
    W->>G: Exchange code for tokens + userinfo email
    W->>DB: Encrypt tokens (AES-GCM) -> UPSERT ga4_oauth_tokens
    W-->>AP: HTML-escaped result page -> postMessage(origin)
1
App-Scoped PBKDF2 Auth: Bootstrap initializes the first user; subsequent signups validate email format, check invite-key app scope, and atomically claim the key (WHERE used_by IS NULL) using 100K-iteration PBKDF2 + timingSafeEqual.
2
Signed OAuth Initiation: Instead of exposing Bearer tokens in popup URLs, Dashboard fetches the signed consent URL via GET /api/ga4/oauth/authorize?format=json with an Authorization: Bearer header.
3
Callback Verification & Storage: The callback verifies the HMAC-SHA256 state signature and 10-minute TTL, exchanges the code, fetches connected_email, encrypts tokens with AES-GCM, and notifies the opener via origin-scoped postMessage.
